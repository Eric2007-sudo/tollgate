# 一次狗粮：拿真活跑一遍闭环，撞出七个缺口

> 这份文档不是教程，是**战报**。它记录的是「`init → add → start → gate → sync → done → handoff`
> 在真实任务上到底会怎么坏」，以及每个缺口是怎么被发现的、怎么修的、用什么测试钉住的。
> 所有数字都来自本机真实账本与宿主库，没有一处是估的。

## 为什么必须跑真活

机制在测试里全绿，不代表它在真活里成立。测试造的是"最小同构库"：3 轮消息、秒级时间戳、
没有计划建立之前的对话。真实会话恰好相反——几千轮、时间戳是 epoch 毫秒、
**而且一大半轮次发生在计划建立之前**。

这一轮的目标本身也是真活：v0.3 让一份账本能装多个会话，但 `sync` 写进账本的行**没有会话 id**，
钱的来源丢了。做这件事的过程，就是最好的测试用例。

## 计划与过闸记录

计划 `abd2d0`，五步（第五步是救火加进来的）：

| 步 | 干什么 | 过闸 |
|---|---|---|
| #1 | 账本行带 `session`，`report` 按会话分列 | 3 条 |
| #2 | 钉住它：`test_sync.py` 第 19 组 + 看板 `money.by_session` | 2 条 |
| #3 | 文档跟上：`plan-format.md` / `README.md` | 2 条 |
| #4 | 归账边界：`started_ms` + 跳过轮次如实报出 | 3 条 |
| #5 | 修 `add` 的两条假警告 + 这份战报 | 2 条 |

## 七个缺口

### 1. 账本行没有会话来源（这一轮本来要修的）

`sync` 写进 `ledger.jsonl` 的行只有 `step / in / out / reqs / cost`，没有 `session`。
一份账本装多个会话之后，「这笔钱是谁花的」就永久丢了。修法：每行带 `session`，
`tg report` 按会话分列，v0.2 之前的老行单独归「没有会话 id 的旧行」一桶——**不猜**。

### 2. 第一步吃掉整段对话历史（这一轮最值钱的发现）

第一次 `tg sync` 的真实输出：

```text
== 对账（源：opencode.db） ==
  会话 ses_e98e7b99 ｜ 本次同步 1102 轮（上次 sync 之后）
  记入 #1：新输入 2918.4k + 输出 744.7k（其中推理 275.1k）= 3663.1k tok
  钱：$0.486120（¥3.2518） · 宿主记录
```

第 1 步的预算是 8k tok、40 轮，于是 `tg report` 直接炸出：

```text
  #1 1102 轮/40 ｜ 单轮 3.3k ｜ 实耗 3663.1k ｜ $0.486120（¥3.2518）
  #1 记会话 id + report 按会话分列 — 超支（45789%）
```

这 1102 轮里绝大多数发生在计划建立**之前**——写计划、讨论、上一件事的收尾。钱是真的，
归属是假的。它比不记更坏：它会带着你去做错误的决定（砍预算、换模型、给这一步 `block`），
而问题根本不在这一步。

修法：`tg start` 给这一步记下 `steps[].started_ms`，`sync` 只认这之后开始的轮次，
被挡在外面的轮次照样报出来（`skipped`），不藏。重试 `start` 不覆盖边界，
`reset` 清掉；老计划退到 `plan.created`；两个都读不出来时**明说算不出边界**，
把整段算进来并标注只能当上限看。详见反模式 #28。

### 3. 修复本身在真机上崩了（测试没覆盖那条路径）

改完代码、四套测试全绿，真机 `tg sync` 却抛栈：

```text
  File "tg.py", line 2441, in cmd_sync
    % (sk["rounds"], sk["at"], sk["usd"]))
KeyError: 'at'
```

原因：`skipped_payload()` 里我用了 `first` / `last`，输出里却取了不存在的 `at`。
更关键的是**为什么测试没抓到**——那一组只造了「全部轮次都在边界之前」的库
（`fresh == 0`），走的是另一条分支；`fresh > 0 且 skipped > 0` 的分支一行覆盖都没有。
补了第 20a 组：边界前 2 轮 + 边界后 3 轮，六项断言（照记 3 轮 / 报跳过 2 轮 /
跳过的钱 = 2 × 0.0007 / 人读输出里有「跳过 2 轮」/ 有「归账边界」/ 账本只记 3 轮）。

**这条值得单独记住**：测试全绿 + 真机一跑就崩，差的不是数量，是分支形状。
造夹具时要问「这个用例走的是 happy path 还是我等一下才会用到的那条」。

### 4. `add` 的两条假警告

```text
$ tg add --title ... --rounds 20 --out docs/
已加 #5 修 add 的预算误报（tier=cheap，预算 8k，复用=new）
!! 这步预算 8k 还不到一次请求的上下文（30k）。……改用 --rounds 按轮数定预算
```

用户明明已经按轮数定了预算（`--rounds 20`），却被骂 token 预算太小——因为 `--budget`
的默认值 8000 被当成了「用户的选择」。同理，没写 `--reuse` 时会问「为什么选到只能新写」，
可默认档不等于选过。

修法：`--budget` / `--reuse` 的存值都改成「没给就不算用户选择」，警告只在**显式**给了
且确实有问题时才出现。四条测试钉住（给了 `--rounds` 不骂 / 手写 `--budget` 才骂 /
没写 `--reuse` 不问 / 显式 `--reuse new` 才问）。

假警告比没有警告更坏：它教人忽略警告。

### 5. `done` 会重跑全部门禁，而门禁里有一条要跑全部四套件

把 `cmd:python tests/check_doc_counts.py` 放进断言之后，一次 `tg done 4` 要跑：
`test_sync.py`（40 秒）+ `check_doc_counts.py`（它自己再把四个套件全跑一遍）。
实测一次 `done` 超过 2 分钟，直接把我的命令超时打爆。收尾时 `tg reconcile` 更狠——
它要把**所有**已完成步骤的门禁重跑一遍，这一轮 6 个步骤里有 2 条断言要跑全量测试，
180 秒超时被打断（不是挂，是真在跑）。当时给的结论是「给 `reconcile` 至少留 10 分钟」，
后来实测连 900 秒都不够。

这不是 bug，是设计没想清楚：**文档核对器是"提交前"的检查，不是"这一步做完了"的检查**。
收尾时按这个思路改掉两条（0.4.1）：

- **超时不再算 FAIL**，单独标 `TIMEOUT`：`done` 照样拒绝（没验完就别算做完），但
  `reconcile` **不判回归、也不以非 0 退出**，只报 `?? 有 N 条没验完（超时）：不知道还算
  不算通过`。以前超时一律记 FAIL，一步好代码因为跑得慢被报成"现在不通过了"，人会去查
  一个根本不存在的回归——**超时是没结论，不是破窗**。
- **每条 `cmd:` 断言带耗时**，且 `gate` / `done` / `reconcile` 都能 `--timeout N`
  （`0` = 不限时）。慢断言留不留由你定，但不用再猜是哪一条在拖时间。

规矩写进了 `references/gates.md`：断言回答「**这一步**做完了吗」，全仓检查放提交前；
凑成反模式 #29。

**规矩先拿自己的计划开刀**：这个狗粮计划里有 4 条断言在跑整套文档核对（#3 #4 #6 各一条，
`test_sync` 那两条也算全量）。真机实测：改之前 `tg reconcile` 跑 900 秒还没完，被我自己的
超时打死，连输出都没留下；把 #3 #4 的两条全仓检查移走（`tg amend 3 --force --rm-accept …`，
ledger 里留了 `amend` + `forced` 记录，改动可审计）、只在 #6 收尾保留一条之后，
**同一条命令 352 秒跑完，全部仍然通过**。剩下的时间主要花在 `test_sync.py` / `test_tg.py`
上——那两条是这个项目的正当断言（这一步的产物就是代码和测试），不算滥用。

### 6. 「跳过多少钱」会被读成「漏了多少钱」（写战报时才发现的）

边界上线后第一次真机输出里有这么一行：

```text
  跳过 1213 轮（2026-10-23 12:50:07 ～ 2026-10-25 16:35:45，共 $0.553181）
```

$0.553181 是那 1213 轮在宿主里的真实花费——**可其中 \$0.542841 早就记在账本里了**
（#1 那笔）。把它报成一个总数，等于暗示"账本漏了 55 美分"，方向刚好反了。
金额没错，读法错了；这类数比不报更坏。

修法：`skipped` 里拆成「已在账本里的」和「从没入过账的」两半，JSON 字段是
`accounted` / `usd_accounted` / `unaccounted` / `usd_unaccounted`：

```text
  跳过 1213 轮（2026-10-23 12:50:07 ～ 2026-10-25 16:35:45，共 $0.553181）：那段时间这一步还没开始
    其中 1190 轮 / $0.542841 已经在账本里了（更早的 sync 记的，不是漏账）；剩 23 轮 / $0.010340
    从没入过账 —— 它们不属于这一步，所以也不记。
```

### 7. 简报把自己的产物列成了「别人的东西」（第 6 步 `handoff` 时发现的）

收尾那一步的产物是 `docs/`，可简报的「明确不在范围内」里赫然写着：

```text
## 明确不在范围内
下面这些文件属于**别的步骤**，这一轮不要动：
- `docs/`
- `tg.py`
- `tg.py`        ← 同一行出现两次
- `tests/`
```

它把**自己**的产物列为「范围外」，还重复列了文件。执行者（尤其便宜模型）照着做，
就会一边要写 `docs/`、一边被告知不许动 `docs/`——这不是风格问题，是自相矛盾的指令。

修法：`out` 与自己的产物相同时跳过，并按出现顺序去重。顺手修了同一处的档位措辞：
「复用梯子：2 仓库里已有 —— 先确认前 6 级都不成立」原来是写死的 6，
选第 2 级时该说「前 1 级」。三条测试钉住（自己的产物不出现 / 不重复 / 级数与档位一致）。

简报是给**不看对话历史的人**（或模型）看的，一个字写错就是一次误操作。

## 边界上线后的真实输出

第 5 步 `start` 之后立刻 `sync`，所有轮次都在这一步开始之前：

```text
$ tg sync
没有新轮次：会话 ses_e98e7b99 最近 1213 轮都已入账。
  跳过 1213 轮：它们早于这步开始的时间（2026-10-25 16:35:54），不属于这一步。
```

再干了一会儿再 `sync`，边界两侧都有轮次——这段是完整真输出：

```text
== 对账（源：opencode.db） ==
  会话 ses_e98e7b99 ｜ 本次同步 33 轮（上次 sync 之后）
  这个会话已入账 1265 条轮次；账本里共有 1 个会话的游标
  归账边界：2026-10-25 16:35:54 —— 这步开始的时间；更早的轮次不是这一步花的，不计入
  跳过 1213 轮（2026-10-23 12:50:07 ～ 2026-10-25 16:35:45，共 $0.553181）：那段时间这一步还没开始
    其中 1190 轮 / $0.542841 已经在账本里了（更早的 sync 记的，不是漏账）；剩 23 轮 / $0.010340
    从没入过账 —— 它们不属于这一步，所以也不记。
  记入 #5：新输入 14.8k + 输出 8.4k（其中推理 7.4k）= 30.6k tok
  缓存读 2824.3k / 写 0 —— 不计入预算：命中只是便宜的重读，不占新 token
  钱：$0.016064（¥0.1075） · 宿主记录
```

这就是边界在干活：1213 轮全部不计入第 5 步。修复前，这 1213 轮会安静地全部记到第 5 步
头上；而"跳过多少钱"那一行还多问了一句——**这些钱是漏了还是早记过了**。
答案多半是后者（1190 轮早就入账了），不拆开说，读的人会以为账本漏了 55 美分。

## 账本里那笔错账怎么处理

第 1 步那笔 1102 轮 / \$0.486120 是错归属的产物（当时边界还没修）。**保留，不删**：

- 账本是只追加的审计流水，删行等于伪造历史；
- 它的 `session` 字段是对的，只有"归到第几步"是错的；
- `docs` 与报告里都写明这笔的来源，读的人知道该怎么看。

当前账本（五笔，同一会话）：

| 步 | 轮数 | 新输入 | 输出（含推理） | cache_read | 钱 |
|---|---|---|---|---|---|
| #1 | 1102 | 2918.4k | 744.7k（推理 275.1k） | 72789.9k | \$0.486120 |
| #4 | 88 | 165.5k | 41.3k | 7170.2k | \$0.056721 |
| #5 | 42 + 33 | 137.8k | 33.7k | 5943.8k | \$0.046829 |
| #6 | 35 | 127.7k | 14.0k | 2646.3k | \$0.028316 |

合计 \$0.617985（¥4.1338）/ 1300 轮，单轮 \$0.000475。**这是下限**：`sync` 一次只认一个会话，
同期另有 4 个会话合计 \$38.807691 没进这个账本，差两个数量级。

`cache_read` 那一列（合计 88550.1k）看着比新输入大 26 倍，但它**不进预算求和**——
按中转价，缓存命中的单价是输入价的 1/50。把它并进预算，每一步都会显得超支 19 倍以上，
于是你会去治「上下文太大」这个假病，而真正该改的是轮数。

## 这一轮改了什么

- 代码：`sync` 行带 `session`；`cost_by_session()`；`report` 按会话分列；
  `ts_ms()` / `sync_boundary()` / `boundary_payload()` / `skipped_payload()` / `skipped_lines()`；
  `start` 写 `started_ms`、`reset` 清、`sync` 按边界过滤；`--budget` / `--reuse` 的假警告；
  `handoff` 简报不再把这一步自己的产物列成「范围外」、去重、档位措辞按级数算；
  `run_check(..., timeout=)` / `is_timeout()`、`gate` / `done` / `reconcile` 的 `--timeout` 与
  `TIMEOUT` 结果分类、每条 `cmd:` 断言输出耗时。
- 测试：196 → 264 项（`test_sync.py` 74 → 106，`test_tg.py` 65 → 98，其余不变）。
- 文档：`README.md` 口径与实测样本、`references/plan-format.md`（`started_ms` 与 `boundary`）、
  `references/anti-patterns.md` #28 与 #29、`references/gates.md`（超时语义 + 别把全仓检查
  写进断言）、`docs/architecture.md`（`sync` 数据流加边界）、这份战报。

## 结论

狗粮的价值不在"验证它能跑"，而在**它逼你说出哪里在撒谎**。这一轮最贵的两条都不是功能缺失：

1. 钱算给了错的人（1102 轮 / \$0.486 记到第 1 步）——数是真的，归属是假的；
2. 测试全绿但真机崩——覆盖了分支的一边，没覆盖另一边。

两条都属于"不会报错、只会让你做错决定"的那一类。这类缺口靠读代码读不出来，只能靠真活撞。

## 第二次真活：开工七问第一次被真用（第 10–11 步）

前一轮的七问只是"工具能算"，没人真拿它派过活。这一轮拿它派了：给看板加一块
「人确认进度」面板，两路并发。

**七问的答案（②④⑤ 是人答的，⑥⑦ 是工具给的固定命令）：**

| 问 | 答案 |
|---|---|
| ① 并发几路 | 2 路（上限 2 路） |
| ② 哪个是大脑 | `kernel`（契约持有者，自己不再改 `tg.py`） |
| ③④ 每路只碰哪、做什么 | `frontend`→`ui/`；`tester`→`tests/` |
| ⑤ 谁合、合不上怎么办 | 主会话合；先 `tests/smoke_serve.py` 全绿，再逐条核对面板措辞是否对上契约；对不上先改契约再返工 |
| ⑥ 怎么观察进度 | `tg status` / `orch rollup` / `tg serve` |
| ⑦ 怎么算跑通 | `tg gate 11` 的 exit code 为 0 |

**为什么能拆成两路：** 第 10 步先把契约写死（`contract/reviews-api.md`：字段、`null` 的含义、
面板上那句话的措辞），第 11 步两路各在自己的目录里实现。`tg.py` 谁都不许动 —— 边界是目录，
不是"我尽量只改我那块"。

**账（按会话分列，账本口径，不是估的）：**

| 步骤 | 会话 | 轮数 | in | out | cache_read | cost |
|---|---|---|---|---|---|---|
| #10 主会话 | `…FqsCAt89` | 22 | 123 479 | 14 029 | 1 958 400 | \$0.026163 |
| #11 `frontend` | `…S7KQyDY6` | 45 | 29 027 | 18 016 | 1 186 176 | \$0.014927 |
| #11 `tester` | `…ALYSYiJo` | 19 | 17 948 | 10 152 | 294 016 | \$0.007706 |

合计约 \$0.049（¥0.33）、86 轮、212.7k tok。两路都超了 8k / 10 轮预算（75.1k / 64 轮累计）——
预算没拦住，是因为预算本来只报数、不拦人。**归账处有一处不干净**：主会话只有一条游标，
它的 22 轮里既有第 10 步的契约与后端、也有第 11 步的合并，分不开，整段记在 #10，报告里说清。

**这一轮真撞出来的三处工具问题（都还没修）：**

1. 简报里把文件当目录写：角色 `--dir tg.py` 被渲染成「不许读改 `tg.py/`」（多了斜杠）。
2. 角色简报的"这一步的边界"整段用的是**步骤级**字段：`tester` 的简报上写着
   「产物目录：`ui/`」「前端拿不到契约里的字段就停下来」（那是 `frontend` 的停止条件）。
   这行会真把 tester 推向越界，是最危险的一处。
3. 每份简报的验收断言都是**步骤级全量**：`frontend` 的简报里也有
   `cmd:python tests/smoke_serve.py`，而那条测试是 `tester` 正在同批写的 ——
   于是"先跑通自己那一路"在事实上不可能。

**一处口径偏差（不是 bug，是我给的样本描述不准）：** 一个 review 只有 `checks`（2 条）而没有
`human_confirmed_claims` 时，`total` 是 `2` 而不是 `null`（逐条 claim 数据在，只是一条都没标确认），
显示的是「一条都没人确认（0/2）」。`null` 只留给"连 claim 列表都没有"的那种文件。
契约里本来就该这么读，是我在派活时把样本描述写窄了。

**关于"效率有没有提升"：这一轮不回答这个问题。** 全程只有一个对照组都没有的样本，
