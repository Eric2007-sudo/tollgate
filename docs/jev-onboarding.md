## 二、接通过程里踩到的三个坑

### 坑 1：key 里带下划线，被提取正则截断了

key 形如 `apikey_<32hex>_<64hex>`（108 字符）。用 `apikey_[A-Za-z0-9]+` 去抓，
会在**第一个下划线**处停下，得到 43 字符，服务端回 **HTTP 401**。

于是很容易得出「key 失效」的结论——错的。抓包看到 `Authorization: Bearer` 后面只有 50 字符
（`Bearer ` + 43）才反应过来。**字符集要写成 `[A-Za-z0-9_]+`。**

教训：401 只说明「服务端不认这份凭证」，不说明「这份凭证不存在」。两者差别很大，
前者还能查出是自己发的请求有问题。

### 坑 2：本区域直连被 451 挡住，跟凭证无关

```
直连 api.typesafe.ai  → HTTP 451 {"title":"Typesafe is not available in your region."}
走本机代理           → 鉴权通过（错误请求体回 422/400，不再是 401/451）
```

所以：**看到 451 别去换 key，看到 401 别去查网络。** 两个错误指向完全不同的东西。
`jev` 的 MCP 配置里必须带代理环境变量：

```json
"environment": {
  "NODE_USE_ENV_PROXY": "1",
  "HTTP_PROXY": "http://127.0.0.1:<port>",
  "HTTPS_PROXY": "http://127.0.0.1:<port>",
  "NO_PROXY": "127.0.0.1,localhost"
}
```

注意 `NODE_USE_ENV_PROXY=1` 是要显式给的：Node 不会自动读 `HTTP_PROXY`。

### 坑 3：`mcp` 配置多了一层 `servers`，它从来没被加载过

```jsonc
// 错的：多一层 servers，opencode 不认，jev 的工具根本不会出现
"mcp": { "servers": { "jev": { ... } } }

// 对的
"mcp": { "jev": { ... } }
```

判断方法：会话里看不到 `jev_verify` / `jev_gate` 这些工具，就是没加载上；
别去怀疑 key，先去数括号。

## 三、双轨是怎么记的

原则只有一条：**真值先算完，再问 jev。** 顺序反了就不是验证，是给结论找理由。

- **真值轨**：本地机械算 —— 数文件、跑 grep、真跑那条命令。不参考任何模型输出。
- **语义轨**：jev 的返回**原样落盘**（`.plan/jev-review-<n>-raw.json`），
  映射成 `review-<n>.json` 是后处理。映射写错了就**拿原始返回重算，不重问模型** ——
  重问一次就多一次「挑到想要的结果」的机会。
- **调用账**：每次调用都记（含失败、含因为自己写错映射而重跑的），
  `.plan/jev-calls.jsonl`。只记成功那次等于把成本藏起来。

### 合成样本：6 条 claim，4 真 3 假

故意混进 3 条假 claim。否则一个永远说 `verified` 的橡皮图章也能拿满分——
那不叫验证通过，那叫没验。

| id | claim | 机械真值 | jev | 一致 |
|---|---|---|---|---|
| T1 | README 声明五套测试合计 454 项，且等于各套件之和 | 真（454 = 213+25+115+66+35） | `verified` p=0.86 | ✅ |
| F1 | README 声明合计 **372** 项 | 假（实际 454） | 不支持（contradicts=1.00） | ✅ |
| T2 | `tg.py` 的 `start` 支持 `--max-fanout` | 真 | `verified` p=1.00 | ✅ |
| F2 | `DRIFT_MAX_DEPTH` 的值是 **5** | 假（实际 3） | `contradicted` p=1.00 | ✅ |
| M1 | 454 项测试覆盖了 jev 判定路径，所以 jev 受回归保护 | 假（测试里没有任何模型调用） | 证据不足（contradicts=0.45 / says_nothing=0.53） | ✅ |
| T3 | 花费到上限后 `start` 拒绝而不是只警告 | 真 | `verified` p=0.67 | ✅ |

`M1` 是这里面最有用的一条：它**句子通顺、听起来合理**，而事实是测试从没调过 jev。
jev 没被它骗过去（判成证据不足而不是 `verified`）。

但 n=6 什么也证明不了。它只说明「明显真假跟得住」，**不能当准确率用**。

### 真步骤：第 9 步（C3，钱到上限拒绝 start）

喂进去的是**真补丁**（`git show d9f7f15`，15 123 字节）+ **真测试输出**
（`python tests/test_tg.py`，exit 0），没经过我改写。

```
5 条 claim      → 全 verified（最低一条 p=0.81，最高 0.99）
safe_to_apply   → 0.68   （auto_accept 门槛 0.8，没过）
composite       → 0.79   （门槛 0.7，过了）
action          → review
```

值得注意的是它**没有盖章**：claims 全过，但它仍然说「还得人看一眼」，
理由码是 `safe_to_apply_below_auto_accept` + `confidence_below_auto_accept`。
一个只会点头的 reviewer 在这里会说 `auto`。

`rollup` 把它记成 `unsure 概率 0.81` —— 这是对的，因为 `action=review` 就不该被读成 pass。

## 四、人还没做的那部分（就是唯一没做完的部分）

抽查包的形状：每条 claim 配一条能当场跑的命令 + 真实输出 + 「应该看到什么」，
人只需要看「实际」和「应该」对不对得上，一条 10 秒。

机器复核 5/5 一致，**人确认 0/5**。这两件事不是一回事，
把「机器复核过了」写成「验证通过」就是 `orchestration.md` 里禁的那句合体话。

抽查包本身也翻过车：第一版我把 `tg start` 写成不带步骤号的命令，
三条「不一致」全是我自己的命令错（`--force` 那条更离谱，我拿 `--help` 里出现过 `--force`
当成「有后门」，而它其实只跳过依赖检查，钱闸那段代码根本不看 `force`）。

**抽查工具坏了会造出假警报。正确反应是修工具，不是把标准降下来将就它。**

## 五、已知边界

1. **jev 在云上。** 喂进去的 diff 会离开本机。别把敏感代码整段丢给它，或者先摘要再喂。
   这条和「离线零外传」是矛盾的——真要零外传，只能用 `reviewer=none`（只跑断言）或本地兜底。
2. **它买的是「另一种看法」，不是「更准的结论」。** 三层门控里它那层永远不能否决 `done`。
3. **验证脚本没进仓。** 它们要联网、要 key，进仓就破坏了「454 项全部离线可复现」这条约束。
   数字和结论写在这里，脚本本身是一次性的。
4. **n 太小。** 6 条合成 + 1 个真步骤 + 5 条抽查，够用来发现「它会不会被骗」，
   不够用来声称任何准确率。
