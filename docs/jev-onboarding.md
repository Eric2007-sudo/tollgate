## 二、接通过程里踩到的六个坑（前三个是接口，后三个是我自己）

### 坑 1：key 里带下划线，被提取正则截断了

key 形如 `apikey_<32hex>_<64hex>`（108 字符）。用 `apikey_[A-Za-z0-9]+` 去抓，
会在**第一个下划线**处停下，得到 43 字符，服务端回 **HTTP 401**。

于是很容易得出「key 失效」的结论——错的。抓包看到 `Authorization: Bearer` 后面只有 50 字符
（`Bearer ` + 43）才反应过来。**字符集要写成 `[A-Za-z0-9_]+`。**

教训：401 只说明「服务端不认这份凭证」，不说明「这份凭证不存在」。两者差别很大，
前者还能查出是自己发的请求有问题。

### 坑 2：本区域直连被 451 挡住，跟凭证无关

```
直连 api.typesafe.ai  → HTTP 451 {"title":"Typesafe is not available in your region."}
走本机代理           → 鉴权通过（错误请求体回 422/400，不再是 401/451）
```

所以：**看到 451 别去换 key，看到 401 别去查网络。** 两个错误指向完全不同的东西。
`jev` 的 MCP 配置里必须带代理环境变量：

```json
"environment": {
  "NODE_USE_ENV_PROXY": "1",
  "HTTP_PROXY": "http://127.0.0.1:<port>",
  "HTTPS_PROXY": "http://127.0.0.1:<port>",
  "NO_PROXY": "127.0.0.1,localhost"
}
```

注意 `NODE_USE_ENV_PROXY=1` 是要显式给的：Node 不会自动读 `HTTP_PROXY`。

### 坑 3：`mcp` 多了一层 `servers` —— 这条结论后来被我自己的实测推翻了一半

```jsonc
// 我原来写的形状：多一层 servers
"mcp": { "servers": { "jev": { ... } } }

// 官方 canonical
"mcp": { "jev": { ... } }
```

当时我在文档里写的是「多一层 `servers`，opencode 不认，jev 的工具根本不会出现」。
**这句是没验证就写下的，现在撤掉。** 复核时（2026-06）实测：

```bash
opencode mcp list      # 嵌套形状下：✓ jev connected ／ ✓ claude-mem connected
# 拍平成 mcp.jev 之后：✓ jev connected ／ ✓ claude-mem connected  —— 一样
```

也就是说这一版 opencode **两种形状都读**，嵌套那层不是「加载不上」的原因。
真要挑毛病，问题在另一处：`~/.config/opencode/` 里的 `opencode.json` 和 `opencode.jsonc`
会被**合并**（`opencode debug config` 能看到两份 document 都被读进来），jev 只写在 jsonc、
claude-mem 只写在 json——混着两种形状，下次换版本或改错一处，没人说得清是谁生效。
所以 `opencode.jsonc` 里已经拍平成 canonical 形状（改前备份在同目录 `.bak-*`）。

判断方法也修正：**不要用「工具在会话里没出现」倒推配置形状**，直接跑
`opencode mcp list` 看真实状态；工具没出现还有别的可能（进程没起来、代理断了、key 无效）。

### 坑 4：验收这条路挂在一个会挂的代理上

第 7、8 步的语义轨是**没跑成**的：`jev-mcp` 报 `provider typesafe: request failed`。查下去发现：

```
127.0.0.1:10090   上一次能用，现在整个端口没了（连都不通）
127.0.0.1:7897    CONNECT api.typesafe.ai:443 → 200 Connection established
                  紧接着 TLS 握手 → SSLEOFError
                  同一时刻 github.com / google.com 也一样 → 不是 typesafe 的问题
```

也就是说：**代理进程在跑，上游节点是死的。** CONNECT 返回 200 只代表「本机代理愿意转发」，
不代表「它真的能出去」——拿 CONNECT 的 200 当作网络可用，就会把「我这里没网」
误记成「服务端挂了」。

这件事的教训不在 jev，在**验收流程自己**：

- 语义层是**可选层**。它挂掉时断言层必须照常工作，`tg` 一行都不用改。
- 验收脚本要在**请求真发出去之后**才记账；请求根本没出去时 `usage` 记 `null`，不记 `0`。
  记 `0` 就是谎报「调用过且免费」。
- 「验证没做完」和「验证失败」不是一回事，文档里要分开写。
  第 7、8 步先是因为网络**没做**，代理恢复后各自补做了一次 —— 但两次都没一次跑成，
  原因各不相同，且都不是 jev 的锅（见坑 5、坑 6）。

### 坑 5：喂给 reviewer 的证据不构成证据，它会照实说「不支持」

第 7 步（C1）第一次跑，4 条 claim 判成 **2 `verified` / 2 `unsupported`**（p=0.26、0.06），
理由码里有 `claims_unsupported`。当时那两条是：

- 「doing 默认上限 2 路，超出时 `tg start` 拒绝、要显式 `--max-fanout`」
- 「多路 doing 时 `sync` / `resume` 不替人挑一个」

代码里这两条都是真的，测试也确实通过了。问题在我喂的材料：我只给了**测试名字**
（`OK start 3 --max-fanout 3` 这种），而名字里既没有默认值 2、也没有拒绝文案。
拿「有个用例叫这个名字」去证明「默认上限是 2」，本来就不成立。

补证后（把整份 218 行测试输出原文给它，跟第 9 步一样），同 4 条 claim → **4/4 `verified`**
（最低 0.70）。**同一份代码、同一个问题，只换了材料。**

这条的用法是双向的：

- 它说明 jev **不是橡皮图章**——证据薄的时候它说「不支持」，而不是顺着你的话点头。
  这比 6/6 全绿更有信息量。
- 它也让「换个问法再问一次」变得危险：只要肯加材料，总能问到 `verified` 为止。
  所以补证必须**先说得清缺陷在哪**（这次：测试名 ≠ 断言值），并且**每一次都记账**。
  账本里第 7 步是 3 次调用，不是 1 次 —— 这就是那条纪律的可见形态。

### 坑 6：`verdict` 和补丁级 `action` 是两个问题，混成一个字段会写出自相矛盾的文件

第 8 步（C2）第一次汇总出来是 `verdict=fail` 配 `probs.pass=0.95` —— 一份文件自己打自己。
查下去是我的映射：jev 返回里有两个不同层级的 `action`：

| 字段 | 回答的问题 | 第 8 步的值 |
|---|---|---|
| `verification.action` | 这些 claim 站得住吗 | `auto`（4 条全 `verified`，0.99–1.00） |
| `action`（顶层） | 这个**改动**能不能自动放行 | `escalate`（`confidence_below_review`） |

拿顶层 `action` 去填 `verdict`，等于用「补丁该不该自动放行」回答「claim 成不成立」。
现在两个字段分列写：`rubric.claims_action` 和 `rubric.action`，`verdict` 只由 claim 层决定
（有 `contradicted` → `fail`；有 `unsupported` 或 `claims_action≠auto` 或最低概率 < 0.8 → `unsure`；
否则 `pass`）。

顺带一个读法上的坑：`verification.summary.needs_review` 数的是「单条 claim 的 action 是 review
的条数」，**不是**「没验出来的条数」。第 9 步是 `verified=5, needs_review=2`，
看到 2 别以为有两条没验过。

## 三、双轨是怎么记的

原则只有一条：**真值先算完，再问 jev。** 顺序反了就不是验证，是给结论找理由。

- **真值轨**：本地机械算 —— 数文件、跑 grep、真跑那条命令。不参考任何模型输出。
- **语义轨**：jev 的返回**原样落盘**（`.plan/jev-review-<n>-raw.json`），
  映射成 `review-<n>.json` 是后处理。映射写错了就**拿原始返回重算，不重问模型** ——
  重问一次就多一次「挑到想要的结果」的机会。
- **调用账**：每次调用都记（含失败、含因为自己写错映射而重跑的），
  `.plan/jev-calls.jsonl`。只记成功那次等于把成本藏起来。

### 合成样本：6 条 claim，4 真 3 假

故意混进 3 条假 claim。否则一个永远说 `verified` 的橡皮图章也能拿满分——
那不叫验证通过，那叫没验。

| id | claim | 机械真值 | jev | 一致 |
|---|---|---|---|---|
| T1 | README 声明五套测试合计 454 项，且等于各套件之和 | 真（454 = 213+25+115+66+35） | `verified` p=0.86 | ✅ |
| F1 | README 声明合计 **372** 项 | 假（实际 454） | 不支持（contradicts=1.00） | ✅ |
| T2 | `tg.py` 的 `start` 支持 `--max-fanout` | 真 | `verified` p=1.00 | ✅ |
| F2 | `DRIFT_MAX_DEPTH` 的值是 **5** | 假（实际 3） | `contradicted` p=1.00 | ✅ |
| M1 | 454 项测试覆盖了 jev 判定路径，所以 jev 受回归保护 | 假（测试里没有任何模型调用） | 证据不足（contradicts=0.45 / says_nothing=0.53） | ✅ |
| T3 | 花费到上限后 `start` 拒绝而不是只警告 | 真 | `verified` p=0.67 | ✅ |

> 这三行里的 `454` / `66` 是**当时的读数**：后来给 `orch` 加了「开工七问」那批断言，
> 合计变成 489（`test_orch.py` 66 → 101）。结论没变（数字仍然自洽），
> 但原样保留当时的数，不把旧结论改写成现在的样子——改数字比改结论更容易变成撒谎。

`M1` 是这里面最有用的一条：它**句子通顺、听起来合理**，而事实是测试从没调过 jev。
jev 没被它骗过去（判成证据不足而不是 `verified`）。

但 n=6 什么也证明不了。它只说明「明显真假跟得住」，**不能当准确率用**。

### 真步骤：三步各一次（都是真补丁 + 真测试输出）

喂进去的东西都是仓库原文：`git show <commit>` 的真补丁，加
`python tests/test_tg.py` 的整份输出（218 行，exit 0）。claim 不是我编的，
是这三步在计划里的 `accept` 断言 + 对应到的那几条 `OK` 行。

| 步骤 | claim | jev | 最低概率 | `claims_action` | 补丁级 `action` | verdict |
|---|---|---|---|---|---|---|
| 第 9 步 C3 | 5 | 全 `verified` | 0.81 | `review` | `review` | `unsure` 0.81 |
| 第 7 步 C1 | 4 | 全 `verified`（补证后） | 0.70 | `review` | `review` | `unsure` 0.70 |
| 第 8 步 C2 | 4 | 全 `verified` | 0.99 | `auto` | `escalate` | `pass` 0.99 |

值得注意的三件事：

1. **它一次 `auto` 都不肯白给。** 第 9 步 claims 全过，但 `safe_to_apply=0.68` < 0.8，
   它说还得人看一眼；第 7 步最低概率 0.70 也让它停在 `review`。只有第 8 步
   claims 全部 0.99+ 才给 `auto`，而补丁级仍然 `escalate`。一个只会点头的 reviewer
   在这三处都会说 `auto`。
2. **claims 全过 ≠ 这个改动可以自动放行。** 第 8 步就是反例：claim 层 `auto`、
   补丁层 `escalate`。这两件事必须分开看（坑 6）。
3. **人工抽查只做了 2 条。** 上面每一行都是「机器算的真值 + 模型的概率」，到 2026-06 为止
   只有 7.4（`resume` 不替你挑）和 8.3（成环说清楚了）两条有人确认过，其余 11 条没有。

前两件合起来正是三层门控想要的形状：**断言管生死，reviewer 只出概率，人只在两层打架时介入。**
目前三层里第三层完全空着 —— 所以这些 `verified` 现在只能叫「另一种看法」。

## 四、人还没做的那部分（就是唯一没做完的部分）

人只需要看「实际」和「应该」对不对得上，一条 10 秒。

现在覆盖三步，共 13 条，其中标 ★ 的 3 条必查（`.plan/jev-spotcheck-7-8.md` 是三步合并版，

第 8 步第 4 条只确认了一半（「不再逐条报深度」这半句由 8.3 那行看到，
「parallel 只用 `stuck` 报」那半句对应 8.4，人没看），所以整条仍记未确认 ——

抽查包本身也翻过车：第一版我把 `tg start` 写成不带步骤号的命令，
三条「不一致」全是我自己的命令错（`--force` 那条更离谱，我拿 `--help` 里出现过 `--force`
当成「有后门」，而它其实只跳过依赖检查，钱闸那段代码根本不看 `force`）。

**抽查工具坏了会造出假警报。正确反应是修工具，不是把标准降下来将就它。**

## 五、已知边界

1. **jev 在云上。** 喂进去的 diff 会离开本机。别把敏感代码整段丢给它，或者先摘要再喂。
   这条和「离线零外传」是矛盾的——真要零外传，只能用 `reviewer=none`（只跑断言）或本地兜底。
2. **它买的是「另一种看法」，不是「更准的结论」。** 三层门控里它那层永远不能否决 `done`。
3. **验证脚本没进仓。** 它们要联网、要 key，进仓就破坏了「489 项全部离线可复现」这条约束。
   数字和结论写在这里，脚本本身是一次性的。
4. **n 太小。** 6 条合成 + 3 个真步骤 + 13 条抽查，够用来发现「它会不会被骗」，
   不够用来声称任何准确率。而且第 7 步那次说明：**同一个模型、同一份代码，
   换个证据就能从 `unsupported` 变成 `verified`** —— 这种敏感度本身就是「不要拿它当测量仪」的理由。
5. **`orch rollup --gate` 很慢。** 它会把 9 个已完成步骤的 `cmd:` 断言全部重跑一遍（每步要跑全套测试），
   本机实测 15 分钟没跑完，只能中断。不带 `--gate` 时它读计划里的状态，并且会明说
   「未重跑，加 --gate 才看得到现在」——那句提示不是废话，是它拒绝假装自己重跑过。
   所以日常看 `rollup` 就别加 `--gate`，要重验整体用 `tg reconcile --timeout 900`（约 6 分钟）。
