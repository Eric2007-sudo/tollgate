# 编排层：多角色并发怎么不炸

`orch.py` 是 `tg.py` 旁边的第二层。它解决的问题不是「怎么让模型跑得更快」，而是
**「让多个 agent 同时干活时，账、边界、验收都不失真」**。

## 它是什么，不是什么

| 是 | 不是 |
|---|---|
| 把「谁负责哪个目录、谁来评」落盘成契约 | 进程调度器（不起线程、不管生命周期） |
| 派发前把四道刹车踩一遍 | agent runtime（不拼 prompt 给模型执行） |
| 把 `.plan/review-*.json` 和账本汇总成三层报告 | 模型调用方（一个 token 都不发） |
| 只经 `subprocess` 调 `tg` 的 `--json` 契约 | `import tg` 内部函数（内核换个实现它也不改） |

最后一条是硬约束：**orch 从不 import 内核**。它只认 `tg status --json` 的 `api` 版本号，
对不上就停，不去猜计划长什么样。这样内核可以单独升级，也可以被换成别的实现。

## 三层门控：生死只由第一层决定

| 层 | 谁说了算 | 输出什么 | 能不能否决 `done` |
|---|---|---|---|
| 1 断言 | `exit code` | 过 / 破 / **超时（没验完）** | 能，唯一能的那层 |
| 2 语义 | reviewer（jev / startlux / local-4b / none） | 概率 + 证据 | **不能**，只出建议 |
| 3 人 | 你 | 只在 1、2 打架时介入 | 能，且是最后一道 |

三条铁律：

1. **报告里不许出现「AI 评价通过」这种合体句。** 两层必须分列打印。合起来写，
   迟早有人拿语义 verdict 当验收依据。
2. **jev 的 `pass` 在人工抽查验证之前不得当作 `done` 依据。** 双轨期要求：每条
   jev 评价旁边记一句 `human_verified`，`orch rollup` 会把「评了几次 / 抽查了几次」
   摆出来，没抽查满就一直警告。**抽查满了也不改这条铁律** —— 它只说明「这一层接对了、
   它说的话有人核过」，不说明「以后可以信它」。
3. **没查就说没查。** `rollup` 不给 `--gate` 时不做打架检测（因为 `status=done`
   只说明「当时过了」，代码可能已经变了），并且明说「没查不等于没打架」——
   绝不输出一个看着像结论的「0 个打架」。

## `review-<step>.json` 格式

放在 `.plan/review-<步骤号>.json`。写它的是**主会话的 agent**（它调 jev 或别的 reviewer），
`orch` 只读不写、只汇总不裁决。

```json
{
  "schema": 1,
  "step": 2,
  "reviewer": "jev",
  "model": "jev-判定",
  "verdict": "pass",
  "confidence": 0.82,
  "probs": { "pass": 0.82, "fail": 0.18 },
  "checks": [
    { "name": "路由与契约一致", "ok": true, "note": "5 条路由全对" },
    { "name": "错误体格式", "ok": false, "note": "缺 code 字段" }
  ],
  "evidence": [
    { "kind": "file", "ref": "api/app.py", "note": "只看了这个文件" },
    { "kind": "diff", "ref": "git diff --stat", "note": "改动 3 个文件" }
  ],
  "reviewed_at": "2026-10-25T21:00:00",
  "reviewer_session": "ses_e8ce09f98ffeH9jKpjw8mxL1bE",
  "cost_usd": 0.0012,
  "human_verified": false,
  "notes": "没跑起来，只做了静态比对 → 概率给低一点"
}
```

字段口径：

| 字段 | 必填 | 口径 |
|---|---|---|
| `schema` | 是 | 现在是 `1`。加字段不升，改含义要升 |
| `step` | 是 | 步骤号，必须和文件名里的号一致 |
| `reviewer` | 是 | `jev` / `startlux` / `local-4b` / `none`，别的一律算坏文件 |
| `verdict` | 是 | `pass` / `fail` / `unsure` / `skip`。**这是概率结论，不是验收结论** |
| `probs` | 否 | 建议给。`{"pass": x, "fail": y}`；只给 verdict 不给概率时，人没法判断该多信 |
| `confidence` | 否 | 0–1。和 `probs.pass` 不是一回事：一个说「我多确定」，一个说「我觉得多可能」 |
| `checks` | 否 | 逐项检查，比一个大 verdict 有用得多 |
| `evidence` | 否 | 它到底看了什么。**只写了 diff 没跑起来** 这件事必须写在这儿 |
| `human_verified` | 否 | 人抽查过才写 `true`，且只有在**全部** claim 都被人确认过时才为 `true`。缺省视为 `false` |
| `checks[].human_confirmed` | 否 | 逐条：这条 claim 人到底看过没有（`true` / `false`），配合 `checks[].human_basis` 写清依据 |
| `human_confirmed_claims` | 否 | `{"confirmed": 1, "total": 4}`。**部分确认不算验证通过**，但「确认了 1 条」和「一条没确认」必须能分开看 —— `orch rollup` 逐条数。全绿（`confirmed == total`）时 `rollup` 换成另一句话说明「全部经人确认」，不再照抄「仍是 false」 |
| `checks[].human_basis` | 否 | 这条依据写清**答复粒度**：是逐条单独答复，还是一次整批答复。人都答了「对」，这两种不是同一件事，不许合并表述 |
| `reviewer_session` | 否 | 评价这件事本身花了哪个会话的钱，能追到账 |
| `cost_usd` | 否 | 评价本身的成本。一次评价也是有代价的，别算进「免费的检查」 |

**坏文件必须报出来。** 缺字段、`reviewer` 不在允许列表、JSON 本身坏了 —— `orch rollup`
会逐条点名。把它当「没评过」静默跳过是最坏的处理：看起来一样，事后没人查得出来。

## 命令

```bash
# 角色 = 一个它独占的目录。目录一重叠就不是并发，是抢文件。
# --task 是「这一路具体做什么」，--lead 标大脑（全计划只能一个），--merge 是「谁看、谁合、合不上怎么办」。
orch role add backend  --dir api/ --task "产出 api 的字段与路由，给前端当唯一事实来源" \
                       --lead --merge "backend 先看接口对不对再合；对不上就改契约文件" --reviewer none
orch role add frontend --dir web/ --task "出界面，只调 api/ 里已定的字段" --reviewer none
orch role list                     # 顺带把「开工七问答到哪了」摊开，缺的写「会拒」

# 派发前踩四道刹车 + 过开工七问，过了就一人一份自足式简报（不派发、不调模型）
orch fan 2                          # 默认全部已登记角色
orch fan 2 --roles backend,frontend --json
orch fan 2 --contract contract/CONTRACT.md

# 换大脑必须两步走（--force 单独一个旗子换不掉，防止「为了推进先换掉拍板的」）
orch role add backend  --dir api/ --force --no-lead --note "为什么换"
orch role add frontend --dir web/ --lead --task "..." --force

# 收工后三层汇总
orch rollup            # 只读计划状态，不做打架检测（并明说没查）
orch rollup --gate     # 真重跑断言，才谈得上「打架」
orch rollup --gate --cost --json
```

`fan` 生成的简报在 `.orch/briefs/<步骤>-<角色>.md`，每份都自带：只能碰的目录、
别人的禁区、唯一事实来源（契约文件）、验收断言原文、归账命令，以及
**「不要自己调 `tg done`」**。

简报里三处的「主语」必须落在这一路身上，写错主语比没有简报更坏——句子都对，agent 会
按它办，办的是别人的活：

| 简报里的位置 | 口径 | 写错的后果 |
|---|---|---|
| 只能碰的目录 / 禁区 | 角色 `--dir` **原样**显示，是文件就写 `tg.py`、是目录才写 `ui/` | 单文件角色写着「不许改 `tg.py/`」，一个不存在的目录 |
| 你这一路的产物目录 | 用**角色**的 `--dir`；步骤级 `out` 另起一段并注明「别拿它当你的边界」 | 步骤 `out` 写的是 A 的目录，B 的简报上印着 A 的边界 |
| 验收断言 | 按「断言点名了谁的路径」分给各路：`grep:/x@ui/app.js` → `frontend`，`cmd:python tests/s.py` → `tester`；认不出归属的算整步 | 一路的简报里塞着另一路正在同批写的测试，于是「先跑通自己那一路」事实上不可能 |

步骤级 `stop` 对所有角色一样，简报里就这么标；里面点了某个角色的名时，`fan` 会当场警告
——那句话对另外几路不生效，别让它冒充别人的刹车。一条自己的断言都没有的那一路，简报会直说
「停下来汇报」，而不是让它自己编一条。

## 派发前的四道刹车

| 刹车 | 默认 | 踩下去的样子 |
|---|---|---|
| 并发路数 | 2 | `要派 3 路，上限是 2 路` —— 并追问「这 3 路各自产出的东西谁看、谁合、合不上怎么办」 |
| 目录重叠 | 必查 | `角色 a 的 api 与 b 的 api/sub 重叠 → 这不是并发，是抢文件` |
| 依赖链深度 | 3 | `依赖链深度 5 > 上限 3` —— 链越长，前面一步判断错，后面全白跑 |
| 契约文件 | 必查 | 没契约只是警告（并说明「各自脑补 = 集成时返工」），显式指定了却不存在是硬拒 |

路数上限不是性能旋钮，是刹车。依据写在下面「凭什么这么设」里。

## 开工七问：并发之前先把这七件事答掉

四道刹车管的是「会不会炸」，七问管的是「炸之前有没有人拍板」。前五问必须由人给答案，
后两问由工具给（命令是固定的，不用人自己发明一套「怎么看进度」）：

| # | 问 | 谁答 | 没有它 / 没有答案会怎样 |
|---|---|---|---|
| ① | 并发几路 | 人 | `--max-fanout`（默认 2）直接拒，并追问「这几路谁看、谁合、合不上怎么办」 |
| ② | 哪个是大脑 | 人 | `role add --lead`。两个 lead = 零个 lead：互相等指令，token 照烧、进度不动 |
| ③ | 几个角色、各碰哪个目录 | 人 | `role add --dir`。目录重叠 = 抢同一批文件，不是并发 |
| ④ | 每路具体做什么 | 人 | `role add --task`。**只有目录不算任务**：指令缺一句，执行的人就会自己发明一句 |
| ⑤ | 谁合、合不上怎么办 | 人 | `role add --merge`。并发最贵的一课是「各自都对，合不上」 |
| ⑥ | 怎么观察进度 | 工具 | `tg status`（谁在 doing）· `orch rollup`（三层分列）· `tg serve`（只读看板，只绑 127.0.0.1） |
| ⑦ | 怎么算跑通 | 工具 | `tg gate <n>` 的 **exit code 为 0**。概率、账本、看板颜色都不算 |

②④⑤ 缺任何一项，`orch fan` 直接拒绝派发（exit 2，**一份简报都不生成**），并把缺口逐条点名：
「`frontend` 具体做什么 —— 没写 `--task`」。`role list` 也会把七问的现状摊开，缺的写「会拒」。

**换大脑不许用一个旗子搞定。** `--force` 单独不解锁换人：要两步，
① `role add <现任> --force --no-lead`（带 `--note` 说清为什么），② `role add <新大脑> --lead ...`。
每一步都记进 `.orch/roles.json` 的 `lead_history`（时间、角色、从谁换成谁、原因）。
理由很实际：只给一个旗子，就等于给「为了让流程往下走，先把拍板的换掉」留了后门。

`fan --json` 里对应 `preflight` 字段（`lead` / `routes[]`（含每路的 `task`）/ `merge` / `observe[]` /
`done_when[]`），下游不用再解析人类文字。

## 并发怎么真落地

`tg start` 允许最多 **2 步**同时 `doing`（`--max-fanout N` 可以调高，理由见下节）。
但上限只是必要条件，真正的条件是**每路一个独立会话**：

1. 每路各开一个 subagent 会话；
2. 每路在**自己的会话里** `tg start <n>` —— 各自拿到 `started_ms` 归账边界，
   不存在「谁先启动就吃掉别人的轮次」；
3. 收工 `tg gate <n>` 点名验、`tg sync --step <n> --session <该路会话 id>` 点名归账
   （游标按会话分开存，来回切也不会重记）。

两条刹车兜住「忘了这么做」：

- 第 3 路会被 `tg start` 直接拒，并追问「谁看、谁合、合不上怎么办」；
- 有 2 步同时 `doing` 时，`tg gate` / `tg sync` **不带编号一律拒绝**，把候选编号列出来。
  猜错等于给错的步骤发通行证、把两路的钱记到一步上 —— **归错比不记更糟**。

反过来，**两路塞进同一个会话**是最坏的情况：轮次混在一起，`sync --step N` 点谁的名
都是猜。账是真的，归属是假的 —— `tg start` 放行时会当场警告这一点。

## 凭什么把路数卡在 2

不是拍的，是两个已公开的实测 + 我们自己的账本：

- **Anthropic 的多 agent 研究系统**：+90.2% 的质量，但花 **15×** token；而且同一篇
  明确说编码任务的可并行度低。
- **MAST**（1642 条多 agent 轨迹的失败模式调查）：头号失败模式是 **cost runaway**。
- **本仓 A/B 实测**（同一个待办 Web 应用，一份写死的契约）：2 路并发 18 轮 / 28.8k tok
  / $0.010047 / 墙钟 111.2s，1 路串行 46 轮 / 72.9k tok / $0.030831 / 518.8s。
  `cache_read` 200.2k vs 1649.7k（差 8.2 倍），质量打平（集成探针均 32/32）。

结论不是「并发更快」，而是：**并发的收益来自「强制先把契约写死 + 角色边界 = 目录边界」**，
钱是从「不重复读」和「少返回几轮」省下来的。所以 `orch` 卡的是路数，逼的是契约。

## 不变量（改代码时别破）

1. `orch` 不调模型、不起进程、不改 `plan.json`。
2. `orch` 的 `stdout` 是机器契约：**人类提示一律走 `stderr`**，警告同时进 payload 的
   `warnings`。破了这条，下游每读一个命令都得猜哪几行是 JSON。
3. `review-*.json` 永远不能改变步骤状态。`orch rollup` 跑完之后 `plan.json` 必须字节不变
   （测试里直接比对前后 status 表）。
4. `tg --json` 的 `api` 版本对不上就停，不降级、不猜。

## 局限

1. 只读 `.plan/plan.json` 的存在性，状态一律问 `tg status --json`；内核崩了 orch 就没事干。
2. 简报是模板生成的，不懂项目语义——它保证「边界和契约写清了」，不保证「任务描述得好」。
3. 依赖深度按 `depends` 图算，不看产物依赖；产物重叠由 `tg parallel` 另外判。
4. `rollup` 的打架检测只在 `--gate` 下做（其它情况一律报「没查」），所以默认模式**不能**
   拿来当验收证据。
5. 不做重试、不做超时、不做并发限流——它只做准备和汇总，执行由主会话掌控。
