# 上下文预算：钱是怎么算出来的

这一篇只讲一件事：`tg ctx` 吐出来的那些钱和百分比，每个数字从哪来、怎么验、什么时候会错。

## 1. 计费公式

宿主（OpenCode）自己就是这么算的，tollgate 只是照抄并核对过：

```
usd = ( input       × price.input
      + (output + reasoning) × price.output
      + cache_read  × price.cache.read
      + cache_write × price.cache.write ) / 1_000_000
```

三个必须记住的点：

1. **`reasoning` 按输出价计**。漏掉这一项，账就对不上——实测里 reasoning 能占输出侧的 80%。
2. **价格单位是 USD / 百万 token**（`Money.USDPerMillionTokens`），所以要除 `1e6`。
3. **`cache_read` 单独一个价**，通常只有 input 价的 2%~30%。这就是"前缀稳定"值钱的原因。

### 验算式例

一次真实请求：`input 3407 / output 6 / reasoning 21 / cache_read 0`，单价 `0.119596 / 0.478383 / 0.002392`：

```
(3407×0.119596 + (6+21)×0.478383 + 0×0.002392) / 1e6
= (407.46 + 12.92 + 0) / 1e6
= 0.000420379913
```

与 `session_v2.cost` 记录值逐位一致。**手算对不上就别信工具。**

## 2. 单轮上下文是什么

```
本轮上下文 = 该轮 input + 该轮 cache_read
```

不是 `output`，不是会话累计。含义是"这一次请求实际送进模型的 token 总量"：未命中部分走 input 价，命中部分走 cache_read 价。

实测一个 128k 窗口的会话第 40 轮：

```
input 227 + cache_read 74.5k = 74.7k   →  占窗口 58%
命中率 227/74700 ≈ 99.7%
```

**命中率极高不代表不用管**：74.7k 里 99.7% 是缓存命中的，但每一轮仍要为这 74.7k 付一次 cache_read 的钱，而且它还在涨。

## 3. 增速与"还有几轮"

```
增速 = 近 8 轮 ctx_tokens 差分的中位数      （只取非负差分）
天花板 = 窗口 × 0.9
剩余轮数 = (天花板 − 当前上下文) / 增速
```

为什么用中位数：一次读大文件会让均值直接翻倍，而中位数只当它是"偶发"。代价是**真正的阶跃会滞后一轮才反映**——这是已知局限，不是 bug。

为什么是 0.9 而不是 1.0：留 10% 给下一轮的输出和一次意外读取。到 100% 时通常已经撞了一次错误了。

## 4. 压缩还是换会话：1.5× 是怎么来的

设当前上下文为 `T`，输入单价 `p`，压缩比 `r = 3`，简报大小 `b = 600 tok`。

```
压缩收益 ≈ T × (1 − 1/r) × p        = T × 0.667 × p
换手收益 ≈ (T − b) × p             ≈ T × p        （T ≫ b 时）

比值 = 换手 / 压缩 ≈ 1 / 0.667 = 1.5
```

**这是一个结构性结论，不是这次数据碰巧。** 只要 `T ≫ b`、`r ≈ 3`，比值就锁定在 1.5 附近——`tg ctx` 在任何会话上都会给出这个数，这一点不要当成"发现"。

真正的差别在两处，也都是结构性的：

1. **换手把上下文打到 600 tok；压缩只削掉 2/3。** 一个是重置，一个是打折。
2. **压缩本身要一次调用**（把大块读一遍再写摘要），这笔开销每轮都要重付；换手是一次性成本。

所以判断规则只有一条：**只要任务还能在 600 tok 的简报里说清楚，就先换手。** 只有在"中间推理必须原样保住、写不进简报"时才压缩。

## 5. 三个阈值

| 常量 | 值 | 含义 | 怎么重标 |
|---|---|---|---|
| `CTX_WARN_RATIO` | 0.5 | 上下文占窗口一半 → 建议换手 | 任务需要大量并行读文件时调低 |
| `CACHE_HEALTH` | 0.30 | 命中率低于 30% → 前缀在漂移 | 前缀频繁变（时间戳、随机采样）时会更常触发，属于预期 |
| `COMPRESS_RATIO` | 3.0 | 压缩比假设 | 取 2~4:1 区间的下沿；保守估计 |

`CTX_WARN_RATIO` 调低会让换手更早发生。换手有成本（要写简报、新会话冷启动），所以只在"继续留下来会更贵"时才换。

## 6. 汇率与"上界"

中转是人民币标价。`opencode.json` 里的 `cost` 用 `人民币价 ÷ 汇率` 折成 USD/百万 token：

```
1 USD = 6.689203 CNY     （open.er-api.com，2026-10-25 00:02 UTC）
```

`tg price` 末尾那句话要说清楚：**这是上界**。中转的分组倍率通常还会再打折，所以真实账单一般低于 `db 记录`，而 `db 记录` 一般低于 `按当前单价重算`。

三个钱的数字何时用哪个：

| 数字 | 含义 | 什么时候信它 |
|---|---|---|
| 消息自带 `cost` | 宿主按当次模型、当次价格算的 | **首选**，逐轮账就靠它 |
| `db 记录`（会话累计） | 宿主累计的 | 会话级汇总信它 |
| `按当前单价重算` | 全按**当前**模型单价重算 | 只当上界；会话换过模型时必然偏高 |

当重算值 > db 记录 10% 以上，`ctx` 会主动提示「记账以 db 为准，重算只作上界」——不要用重算值去对账。

## 7. 这些数字什么时候会错

| 现象 | 原因 | 处理 |
|---|---|---|
| 占比超过 100% | 窗口取自 `limit.context`，中转虚标 | 用 `tg price` 核对窗口，必要时手动改配置 |
| `estimate.tokens = null` | 宿主没把 `tokens` 写进消息行 | 跑 `tg ctx --sample` 建基线，退回采样差值 |
| 增速为 0 | 近 3 轮上下文没变化 | 正常——说明这一轮没加多少东西 |
| 本轮花费为空 | 消息里没有 `cost` 且模型没有价目 | 给模型写 `cost`；`tg price` 会显示"无价目" |
| db 记录明显偏低 | 本会话换过便宜模型，或中转折扣 | 正常情况下**就该偏低**，见上一节 |
