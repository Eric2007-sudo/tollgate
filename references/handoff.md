# 强弱分工：handoff 的完整用法

这份文档讲一件事：**怎么把计划交出去，让便宜模型替你把活干完**。

---

## 为什么这是最大的成本杠杆

一条长会话的成本结构大致是：输入 token 占 90%+，其中 80% 命中缓存（便宜 10~20 倍），
剩下 20% 的未命中输入 + 输出才是真花钱的部分。

于是成本优化的顺序应该是：

| 手段 | 典型效果 | 代价 |
|---|---|---|
| **不做不需要的事**（复用梯子） | 工作量直接减半 | 需要判断力 |
| **换模型执行**（handoff） | 单价降一个数量级（本机中转实测 11.25×） | 需要把计划写清楚 |
| **压缩工具输出**（rtk 等） | 输入 token 减 60~90% | 装个工具 |
| **提高缓存命中率**（稳定前缀） | 命中部分单价降 10~20 倍 | 需要克制改上下文 |
| **少发无用请求**（门禁一次过） | 请求数减少 | 需要写好验收 |

`handoff` 落在这张表的第二行。它不需要你理解缓存，只需要**把一件事想清楚到能写下来的程度**。

反过来，它也有个隐性成本：**想清楚是要花贵模型的 token 的**。
所以它只在「这一步会被重复做很多次」或「这一步很长、很机械」时才划算。

---

## 什么时候该 handoff，什么时候不该

**该 handoff**：

- 机械转换：把 A 格式改成 B 格式、把 20 个文件里的同一种写法批量替换
- 你已经知道答案，只需要有人照着落地（写样板代码、加校验、补测试骨架）
- 大规模重复（10 个模块同样的改法）
- 需要长时间跑、但每一步都不需要判断的活

**不该 handoff**：

- 需要判断的步骤（选架构、定方案、权衡取舍）——这些留给 deep
- 需要探查的步骤（"这个 bug 从哪来"）——deep 也可能要 3 轮，但如果 cheap 要 20 轮就不划算
- 一步就能做完的小事——写简报的开销大于收益
- 你还没想清楚的事——**简报写不出来，本身就是「还没想清楚」的信号**

最后一条最重要。`handoff` 有一个副产品：它是检验计划质量的照妖镜。
写不出简报的步骤，就是没被想清楚的步骤。

---

## 简报里必须有的东西（以及为什么）

`tg handoff N` 自动生成，下面解释每一节的作用。

| 小节 | 为什么必须有 |
|---|---|
| 大目标 | 执行者需要知道「为什么做这个」，否则局部最优会毁掉全局 |
| 你这一步（含档位、预算、梯子） | 预算让执行者知道「翻 40 个文件」是超支信号 |
| 前置产出 | **最关键的一节**。它把「上一步的结论」变成文件路径，执行者读文件而不是重新推导 |
| 允许读的文件 | 没有这一节的执行者会 `ls` + `cat` 一整个目录 |
| 不要读 | 反向约束比正向约束更能防失控 |
| 产物 | 单一、具体、可检查的落盘目标 |
| 验收 | 机器判定，带具体命令和期望 exit code |
| 停止条件 | 防即兴发挥。这是便宜模型最危险的行为 |
| 明确不在范围 | 列出**别的步骤**的产物路径，把"顺手改一下"变成明确的越界 |
| 前提核对 + commit 戳 | 计划可能是三天前写的，代码已经变了 |

## 三种交付方式

### 方式 A：同一会话内切模型（最省事，适合能自主执行的环境）

```bash
tg handoff 5                     # 生成简报
# 在 OpenCode 里执行 /models 切到便宜模型
# 然后说：「读 .plan/brief/05-xxx.md，按它执行」
```

优点：文件系统、终端都是现成的。
缺点：上下文里还有前面的对话残留，省钱效果打折（前面积累的 token 仍然每轮都在输入里）。

**真正省钱的版本**：新开一个会话（`/new`），只贴一句「读 `.plan/brief/05-xxx.md` 并执行」。
新会话的输入从零开始，这是 `handoff` 最大的收益点——**你切断了历史上下文的复利**。

### 方式 B：子 agent（适合并行）

在 OpenCode 里把简报路径交给子 agent 作为任务描述：

```
explore 子 agent → 「读 .plan/brief/05-xxx.md，按它执行，完成后跑 tg gate 5 和 tg done 5」
```

注意子 agent 需要能写文件、能跑命令。只读的子 agent 只适合做简报里的「侦察」类步骤。

**并行前先跑 `tg parallel`**：它只把产物路径不重叠的步骤放同一批。
两个子 agent 同时改一个文件，结果是后写的赢，你还会以为是模型不稳定。

### 方式 C：换工具 / 换人（最彻底的解耦）

简报是普通 markdown，带完整上下文。所以它可以：

- 交给另一台机器上的另一个 agent
- 贴给 Cursor / Codex / Claude Code / 任何有终端的环境
- 交给一个人类同事（这就是「交接文档」）

这是这套设计比"在对话里说清楚"强的地方：**交接物是磁盘上的文件，不是上下文里的一段话**。

---

## 换手要花多少钱（以及「回来」更贵）

先算清楚钱在哪，免得把 handoff 当成一种玄学。

**换手出去**：新会话的第一轮只包含「读简报 + 它真需要的文件」。600 token 的简报按本机中转
flash 价全价算是 \$0.000072 —— 可以忽略。所以 handoff 的成本不在钱上，在**想清楚**上
（写不出简报 = 还没想清楚，见上一节）。

**再回来**：这才是贵的那一半。会话搁一会儿再回去接着干，缓存已经过期（各家 TTL 从几分钟到
几小时不等），那一轮要把整个上下文按**未命中**的价格重读一遍：

| 37.2k 的上下文 | 单价（USD/百万） | 这一轮光前缀 |
|---|---|---|
| 缓存命中 | 0.002392 | \$0.000089 |
| 缓存过期后第一轮 | 0.119596 | \$0.004449 |

差 **50 倍**，而 \$0.004449 约等于 **11 轮**典型量（实测单轮 \$0.000387）。也就是说：
在两个会话之间来回切三次，光重读前缀的钱就够你把这件事在便宜模型上从头再跑一遍。

**结论**：要么一口气把一个会话做完，要么 handoff 之后别再回头。
`tg ctx` 会把「本轮命中率」打出来（实测连续跑的长会话是 99.3%）——
命中率掉下来，通常就是你离开过。

## 完整的一轮长什么样

```bash
# ── 贵模型阶段：审计 + 出计划 ──────────────────
tg init "把 12 个 API handler 统一到新的响应封装" --why "现在 3 种错误格式"
tg exclude "node_modules/" "dist/"
tg add --title "侦察：列出 12 个 handler 的现状差异" \
   --tier deep --budget 20000 --out notes/01-audit.md --reuse existing \
   --accept "file:exists:notes/01-audit.md" \
   --accept "grep:^## handler@notes/01-audit.md"
tg start 1 && tg gate 1 && tg done 1

# ── 中间：把机械活拆成便宜模型能做的步骤 ──────────
tg add --title "改 a~f 六个 handler" --tier cheap --budget 10000 --depends 1 \
   --out src/handlers/a_f.diff --read notes/01-audit.md --reuse existing \
   --accept "cmd:npx tsc --noEmit"
tg add --title "改 g~l 六个 handler" --tier cheap --budget 10000 --depends 1 \
   --out src/handlers/g_l.diff --read notes/01-audit.md --reuse existing \
   --accept "cmd:npx tsc --noEmit"

tg parallel     # 确认 #2 和 #3 可以同时做（产物路径不重叠）

# ── 便宜模型阶段：两个会话 / 两个子 agent 各拿一份 ──
tg handoff 2    # → .plan/brief/02-xxx.md
tg handoff 3    # → .plan/brief/03-xxx.md

# ── 收尾 ────────────────────────────────────
tg reconcile    # 所有 done 的断言再跑一遍
tg report       # 看钱花在哪个档位、复用率多少
```

## 简报好不好，可以量化

`tg handoff` 会报出简报的字符数和估算 token。经验值：

| 简报大小 | 说明 |
|---|---|
| < 400 token | 太薄。执行者一定得自己猜，等于没写 |
| 400~1200 token | 正常区间 |
| > 2500 token | 太厚。要么这一步该拆，要么你把实现细节写进计划了（那是执行者的事） |

第二列的行为在实测里很稳定：简报超过 2500 token 的步骤，通常 `budget` 也定得偏高，
而且最后 `report` 会把它标成「用了不到三成」。

## 失败模式

| 现象 | 根因 | 处理 |
|---|---|---|
| 执行者改了范围外的文件 | 简报里没有「不在范围」一节 | 补上；或是在 prompt 里没让它读简报全文 |
| 执行者反复跑同一个命令 | 验收命令报的错和任务无关 | 补一条 `--stop`：「验收报 X 类错误就停下汇报」 |
| 同一个错误重试 5 次 | 缺 `max_rounds` 熔断 | `tg init --max-rounds 3`（默认值） |
| 简报读起来很含糊 | 计划本身没想清楚 | 回去补 `--read` 和 `cmd:` 断言，别指望换个模型能解决 |
| 便宜模型做不完，deep 重做一遍 | 步骤切得太大 | 拆成 2~3 步，每步一个产物 |

最后一条是判断「这笔钱花得值不值」的标准：
**如果 deep 最后要把 cheap 的活重做一遍，那 handoff 就是负收益。**
所以第一次用的时候，`cheap` 步骤的预算别定太高，先看它能不能做完再放宽。
