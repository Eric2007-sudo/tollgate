# tollgate · 过闸

> 给 agent 的每一轮请求装两道闸：**这轮该不该发**，和**这轮塞多少**。
> 零依赖、单文件 CLI + 本地只读工作台。Python 3.8+，只用标准库。

```
                        ┌──────────────────────────────┐
    用户任务 ──────────▶ │  闸一 · 计划预算              │
                        │  tg init / add / start        │
                        │  gate / done / handoff        │
                        │  「该不该做、谁来做、几轮」    │
                        └──────────────┬───────────────┘
                                       │ 放行
                                       ▼
                        ┌──────────────────────────────┐
                        │  闸二 · 上下文预算            │
                        │  tg ctx / price               │
                        │  「多大、多少钱、还撑几轮」    │
                        └──────────────┬───────────────┘
                                       │ 快满了
                                       ▼
                              tg handoff N  →  换干净会话
```

---

## 它是什么，不是什么

**是什么**

- 一本**落盘的计划 + 一本账**。「这一步做完了吗」只认 shell 断言的 `exit code`——流水全过是 `0`，
  有一条破就是非 `0`，模型自己说「做好了」不能顶替它。
- **两道闸**：闸一管这轮该不该发（计划预算、依赖、并发路数、花费上限），闸二管这轮塞多少
  （上下文多大、多少钱、还撑几轮、该不该换干净会话）。
- **一个编排层** `orch.py`：多角色并发之前先踩四道刹车——路数、目录重叠、依赖链深度、契约在不在，
  再过一遍**开工七问**（谁是大脑、每路做什么、谁合……缺一项就拒派发）。
  它只经 `subprocess` 调 `tg --json`，不 import 内部、不派发进程。
- **一个只读工作台**：标准库 `http.server`，只绑 `127.0.0.1`，校验 Host 头。

**不是什么**（写在这里，省得你试完才发现）

- **不是 agent runtime / 进程调度器**。不派发任务、不起子进程跑 agent、不接管生命周期。
  派发是主会话那个 agent 的事；`orch fan` 只**准备**简报，不执行。
- **不是模型网关。** 不改路由、不接你的 key、不代理请求。`--tier` 只是标签，真要换模型是在会话里换。
- **不是 spec-kit 的替代。** 不生成 spec 模板、不做需求澄清流程。
- **不是公开的多人平台。** 单机自用；账本口径是「这台机器上这个 repo 花了多少」，
  多人共享一个账本会算错归属——而归属算错比不记更坏。
- **不是 IDE 插件。** 没有后台服务、没有常驻进程、没有第三方依赖（含 `orch.py` 与看板）。

一句话：**tollgate 管「做完了吗 / 花了多少」，不管「怎么干」。**

## 为什么要有第二个闸

关于省 token，市面上主流答案是"压缩提示词"。但把这个账算清楚会发现问题不在那儿：

| 手段 | 省的是什么 | 省多少 |
|---|---|---|
| 压缩输入 | 未命中的输入 token | 一次请求的 ~2/3 输入费，**每轮都要重付一次压缩调用** |
| 少写一半代码 | 账单的**分母** | 分子再省也只有 0~13% |
| 换一个干净会话 | 输入侧几乎全部 | 一次性打到 ~600 tok 的简报 |
| 干脆不做这件事 | 100% | —— |

所以顺序必须是：**该不该做 → 谁来做 → 怎么压**。前两件事没做，压缩最多救 13%。

tollgate 就是把这个顺序做成工具：闸一管前两件事，闸二管第三件事，并且**用同一条价格口径把"压缩"和"换会话"放在一起比价**。

## 它糅合了谁的想法

这个项目的每一块机制都不是原创，来源写在下面。**改动**一列是我们实际改掉的部分——不改就只是抄袭，改错了就是自嗨。

| tollgate 里的机制 | 来自 | 改动 |
|---|---|---|
| 计划落盘成文件 + 完成由断言判定 | `planning-with-files` | 断言必须是 shell 真命令，`exit code` 说话；模型自述不算 |
| 依赖图 / 并行批次 / 产物冲突检测 | `ccpm` | 加了"两个步骤写同一个产出物"的冲突检测 |
| 自足式简报（给最弱执行者） | `shadcn/improve` | 简报 ≤600 tok，含禁区、验收命令、停止条件 |
| 同一步重试到上限强制熔断 | `LazyCodex $ulw-loop` | 熔断后必须 `reset n --rounds` 显式重开 |
| 复用七级梯子（最省钱是不做） | `Ponytail` | 梯子档位进计划文件，`report` 统计复用率 |
| 输出侧压缩 | `caveman` | **没抄压缩器**，抄的是"先问这笔压缩值多少钱" |
| 上下文压缩 | `headroom` | 改成与 handoff 的比价：结论是换手恒优 1.5× |
| 按需检索而非全量读 | `codebase-memory-mcp` | 落成计划里的禁读清单 `--exclude` + 产出物声明 |
| 本地只读看板 | `claude-mem` 的 work-view | 用标准库 `http.server` 重写，零依赖、只绑 127.0.0.1、校验 Host 头 |
| 语义评审（只出概率、不判生死） | TypeSafe Jev | **只留概率与证据**，`verdict` 一律不能否决 `done`；三层分列打印，禁「AI 评价通过」这种合体句 |
| 模型档位标签 / 路由 | `claude-code-router` / `laya` | **只保留 `--tier` 标签**，不接管路由——实际路由靠会话内切模型，少一层可坏的中间件 |
| usage 记账与 `cost` | OpenCode 自身 | 不另建账本，直接读宿主的 `session_v2` / `session_message` |
| 轮数口径而不是 token 口径 | 本项目实测踩坑 | 实测 token 预算差 74 倍，于是 `--rounds` 定预算、`--budget` 只当探测器 |

## 快速开始

```bash
git clone <this repo> && cd tollgate
python tg.py price            # 先看看宿主的价目对不对得上
python tg.py ctx              # 这一轮多大、多少钱、还能撑几轮
python tg.py init "把 pipeline.py 拆成可测模块" --why "现在改一处要跑全量"
python tg.py add --title "抽出 io 层" --out "src/io.py" --budget 30000 --rounds 3 \
                 --accept "pytest::test_io"
python tg.py serve            # 打开 http://127.0.0.1:7717/
```

干完一步就 `python tg.py sync` —— 宿主跑掉多少轮、多少 token、多少钱，自动记进账本。
装成 skill：

```powershell
.\install.ps1                              # → ~/.config/opencode/skills/tollgate
.\install.ps1 -Target project -ProjectPath "D:\proj"
```

`.plan/` 目录与 `schema 2` 与上游 `plan-ledger` **完全兼容**：老计划用 `tg` 直接读，`tg` 建的计划 `pl.py` 也读得动。

## 子命令（25 个）

**闸一 · 计划与预算**

```
init  add  amend  exclude  ready  parallel  graph
start  reset  block  spend  gate  done  handoff
reconcile  report  ack  status  show  resume  drift
```

`start` 还带 `--max-fanout N`：默认只允许 **2 步**同时 `doing`，而且**每路必须一个独立
会话**。有 2 步 `doing` 时 `gate` / `sync` 不带编号会直接拒绝并把候选编号列出来——猜错
等于给错的步骤发通行证、把两路的钱记到一步上。理由见局限 #18。

钱也有上限：`init --max-cost 0.5` / `tg amend 0 --max-cost 1.2`（美元）。账本里**已知**花费
到顶后 `tg start` 直接拒绝新步骤，`status` 与 `drift` 也会点出来。只剩一种升级方式：把上限
改高（会写进 ledger 留痕），**没有 `--force` 后门**——否则「上限」就只是一句口号。

这里有个口径必须说清：账本是**下限**（同期别的会话、没 sync 的轮次都不在里面），所以
「已知就超了」意味着实际一定超了——拿下限当上限用只会提前拦，不会放行，这个方向是安全的。
反过来就不安全：如果账本里**一项带真实 `cost` 的记录都没有**（只用手记 `spend`，从不 `sync`），
那这个上限拦不住任何东西，`tg start` 会当场说「拦不住」而不是假装自己在拦。

**闸二 · 上下文与钱**

```
ctx [--json] [--sample] [--session ID]   本轮上下文 / 花费 / 增速预测 / 比价
price                                    列出配置里各模型的价目
serve [--port 7717] [--no-open]          本地只读工作台
```

**两闸交界**

```
sync [--step N] [--dry-run] [--json]     把宿主逐轮真实用量写进账本，取代手填 spend
```

**机器可读输出**：`status` / `parallel` / `report` / `gate` / `sync` / `ctx` 都支持 `--json`。
每条命令的 stdout 上是**一个** JSON 对象，带 `"api": 1` 版本号；`gate --json` 失败时照样
exit 1，`ok`/`exit` 字段与真退出码一致。编排层（`orch.py`）只吃这条契约，从不去抠人类可读
输出里的数字——抠出来的数看着像真的，错的时候没人查得出来。

`status --json` 里 **`doing` 是权威字段**（列表，可能有多项）；`current` 只是「第一个在跑的，
或下一个该做的」。多路并发时别拿 `current` 当「谁在干活」——只看它会漏掉另一路的钱和轮数。
`gate --json` 在多步 `doing` 且没点名时给 `ok: false`、`step: null`、`ambiguous: [编号…]`、
退出码 2，而不是替你挑一个。

## 账不用手记：`tg sync`

闸一原先要人肉记账（`tg spend 3 --in 12000 --out 900 --reqs 2`），可闸二已经能把每一轮的
`tokens` 和 `cost` 从 `session_message` 里读出来了。中间那道缝不该让人去补：

```bash
python tg.py start 2
# ...干活，让 agent 跑几轮...
python tg.py sync                 # 自动把「上次 sync 之后的新轮次」记进 #2
python tg.py sync --dry-run       # 只报数，不写账本、不动游标
```

口径和 `spend` **完全一致**，不另立一套：

| 账本字段 | 取什么 | 为什么 |
|---|---|---|
| `in` | Σ 每轮 `tokens.input` | 新输入；缓存命中不计入 |
| `out` | Σ(`output` + `reasoning`) | 推理 token 按输出价计费，属于新 token |
| `reqs` | 轮数 = 带 tokens 的 assistant 消息条数 | 轮数才是靠谱的预算单位 |
| `cost` | Σ 每轮真实 `cost`；宿主没记就按配置单价重算并标 `cost_est` | 有真账就用真账 |
| `cache_read` / `cache_write` | 单列存进记录，**不参与预算求和** | 命中只是便宜的重读，混进预算会让"该压还是该换手"判断失真 |

游标存在 `.plan/sync.json`，**每个会话各存一份**（schema v2：`sessions: {会话id: ids}`），所以：

- 同一轮**永远不会重复记账**，多跑几次 `sync` 是安全的；
- 换会话不会吃掉别的会话的轮次，**回来也不会重记**（老的 v1 单游标文件读的时候自动升上来）；
- 游标文件坏了就当从没同步过，从头重算，不崩。

这条是踩出来的：以前只有一份游标、换会话就清空，于是「对 A 记完 → 去 B 记一遍 → 回来对 A」
把 A 整段重记了一遍——实测应有的 4 轮 / \$0.0011 被记成 7 轮 / \$0.0014。会话不是一根计数
器，是几根并行的计数器。

三个诚实的边界：**归账只认"这一步开始之后"的轮次**（`tg start` 记下 `started_ms`，
更早的轮次不是这一步花的，跳过并报出来）；**读窗口是最新 2000 轮**，更早的读不到也就不计入，这时输出
会明说，别把那次的 tok 数当成"会话总共跑了多少"（那看 `tg ctx`）；**一次 `sync` 只认一个
会话**，所以账本记的钱是**下限** —— 同期在别处跑的子 agent、另一个窗口、切回官方之前那个
会话，它们的花费都不在里面。这种情况 `sync` 会主动说出来，不等你自己发现：

```text
  钱：$0.373855（¥2.5008） · 宿主记录
  另有 4 个会话同期也在花钱（合计 $38.807691）—— 它们还没入账：要入账就逐个 tg sync --session <id>（每个会话各有游标，来回切不会重记）。
```

（v0.4 起 `sync` 还会在这上面多打两行：`归账边界：…` 和跳过多少轮。真输出见下方「实测样本」，
这里的样本是修复前的，不重跑就不改写它的数字。）

`started_ms` 是狗粮逼出来的：第一次拿真活跑闭环，计划刚建立、`tg sync` 就把**整段对话
历史**记到了第 1 步上——1102 轮 / \$0.486120，预算警告直接炸成 45789%。钱是真的，归属是
假的，比不记更坏。现在边界由 `tg start` 写进 `steps[].started_ms`（重试 `start` 不覆盖，
`reset` 才清掉——重新开始 = 重新计），老计划没这个字段就退到计划建立时间，两样都没有时
**明说算不出边界**，把整段算进来并标注只能当上限看。

上面这行是真实输出：那 4 个会话加起来比这次对账的 $0.37 大两个数量级。要分摊账单，
这个差不能装作不存在。**补账不会翻倍**——逐个 `sync --session <会话id>` 就行，
每个会话各有一份游标，来回切多少次都只记一次。

记完账，`tg report` 的「钱」那一栏才有真数（`spend` 只记 token，记不到钱）；没有 `cost`
的账本会明说"账本里没有 cost"，不会拿 token 数硬折成钱。`tg done` 也会在收尾时拉你一把：
宿主就在本机、这步却没对过账，它会提醒先 `sync` 再标记完成。

账本里每笔 `sync` 记的行都带 `session`（这笔钱是哪个会话花的）。一份账本能装多个会话，
所以「谁花的」不能靠猜——`tg report` 会按会话分列：

```text
  按会话：ses_e98e7b99 $0.435452（1 笔 / 1019 轮） ｜ ses_e8e92ea4 $0.001642（1 笔 / 1 轮）
```

只装了一个会话时这行不出现（没信息量的行也是噪音）。**v0.2 之前写的行没有 `session`
字段**，那些会被归到「没有会话 id 的旧行」单独报一桶——工具不猜它属于哪个会话。
看板的「账本花费」卡片同样会标出「N 个会话」。

## 数据从哪来，钱怎么算

| 数据 | 来源 | 口径 |
|---|---|---|
| 逐轮上下文 | `session_message.data` 的 `tokens` | `input + cache.read` = 这一轮真正送进模型的量 |
| 逐轮花费 | 同一行的 `cost` | 宿主自己算的，优先采信 |
| 账本记账 | `tg sync` 从上面两行推导 | `in`=Σinput，`out`=Σ(output+reasoning)，`cache_read` 单列不入预算 |
| 会话累计 | `session_v2` | 只用于"会话级命中率"，**绝不冒充单轮值** |
| 价格表 | `opencode.json` 各 provider 的 `cost` | USD / 百万 token |
| 窗口 | 模型 `limit.context` | 中转若虚标就对不上，会在 `ctx` 里显形 |

计费公式与 OpenCode 一致（实测逐位对账过）：

```
usd = (input×p_in + (output + reasoning)×p_out + cache_read×p_cr + cache_write×p_cw) / 1e6
```

**推理 token 按输出价计**——漏掉这一项就对不上账。

## 门禁跑太久：超时是「没结论」，不是「破了」

`cmd:` 断言就是个 shell 命令，所以有人（我自己）会把「跑全部四套件」这种**全仓检查**
写进断言。它能过，但代价是 `done` / `reconcile` 每次都要重跑它——实测一次两分半起步，
`reconcile` 6 个步骤要十分钟。于是有两条规矩：

- **断言回答的是「这一步做完了吗」，不是「这个仓库还干净吗」**。全仓检查放在提交前，
  当断言就会跟着每次 `done` 一起跑。
- **超时不算失败，算没验完**。以前超时一律记 FAIL，一步好代码被跑慢冤枉成「回归」；
  现在单独标 `TIMEOUT`、单独计数，`done` 拒绝标记完成（没验完就别算做完），
  `reconcile` 报 `?? 有 N 条没验完（超时）：不知道还算不算通过`，并且**不判回归**：

```text
$ tg gate 1 --timeout 1
[2026-10-25T18:35:14] gate #1 跑全仓检查
  TIMEOUT  cmd:python slow.py
      cmd 超时（1s 上限，已跑 5s）：没验完 —— 既不算通过，也不算破了。放宽时间用 tg gate --timeout N（0 = 不限时），python slow.py

1 条断言超时没验完 —— 既不算通过也不算破了。放宽时间：tg gate 1 --timeout 0（不限时），或给个更大的秒数
```

（上面这条 `slow.py` 是演示脚本 `time.sleep(5)`，数字是真的；把断言换成
`cmd:python tests/check_doc_counts.py` 形状完全一样，只是 5s 变 152s。）

`tg gate / done / reconcile` 都有 `--timeout N`（默认 600 秒/条，`0` = 不限时）。另外每条
`cmd:` 断言现在都会在输出里带**耗时**（`exit=0  5.1s`），谁在吃时间一眼看见，不用猜。

## 编排层 `orch`：多角色并发不炸的那一层

`tg` 管「这一步做完了吗」和「花了多少钱」。当你要**几个 agent 同时干活**时，还会多出三个
问题：谁负责哪块、并发几路、各自说的"做好了"算不算数。`orch.py` 只管这三件，它
**不调模型、不起进程、不改计划**，只经 `subprocess` 吃 `tg` 的 `--json` 契约。

```bash
python orch.py role add backend  --dir api/ --task "产出 api 的字段与路由" --lead --merge "谁看、谁合、合不上怎么办"
python orch.py role add frontend --dir web/ --task "出界面，只调已定字段"   # 角色 = 一个它独占的目录
python orch.py role list                   # 顺带把「开工七问答到哪了」摊开
python orch.py fan 2                       # 派发前踩刹车，过了就一人一份自足式简报
python orch.py rollup --gate --cost        # 收工后三层汇总：断言 / 语义 / 人
```

派发前踩的四道刹车：**并发路数**（默认 2）、**目录重叠**、**依赖链深度**（默认 3）、
**契约文件在不在**。路数上限不是性能旋钮：Anthropic 的多 agent 系统是 15× token 换
+90.2% 且明说编码任务并行度低，MAST 查 1642 条轨迹里头号失败模式就是 cost runaway。

刹车管「会不会炸」，**开工七问**管「炸之前有没有人拍板」：①并发几路 ②哪个是大脑
③几个角色、各碰哪个目录 ④每路具体做什么 ⑤谁合、合不上怎么办（这五问由人答）
⑥怎么观察进度 ⑦怎么算跑通（这两问由工具给固定命令：`tg status` / `orch rollup` /
`tg serve`；`tg gate <n>` 的 exit code 为 0）。②④⑤ 缺一项，`orch fan` 就 exit 2、
**一份简报都不生成**，并逐条点名缺的是哪一路的哪一项。大脑只能有一个，`--force` 单独
换不掉它：换人要两步（先 `--no-lead`，再 `--lead`），每步都记进 `lead_history`。

门控分三层，**生死只由第一层决定**：断言看 `exit code`（唯一能否决 `done` 的）、
reviewer 只出概率、人只在两层打架时介入。`orch rollup` 会把三层分列打印，不会写
「AI 评价通过」这种合体句；`jev` 的 `pass` 在人工抽查验证之前**不得**当 `done` 依据
（第一次接入的验收台账，包括没做完的那部分，见 `docs/jev-onboarding.md`）。

细节（含 `review-<step>.json` 字段级格式）见 `references/orchestration.md`。

## 本地工作台

`tg serve` 起一个只绑 `127.0.0.1` 的只读看板（校验 Host 头，防 DNS rebinding），一屏看到：

- 计划进度条、每步预算 vs 已用、轮数是否超预算、**每步的真实花费**
- **账本花费**：只认账本里宿主记过的 `cost`；一笔都没有时显示「没有」，不拿 token 折算
- **同期在花**：另有几个会话在计划建立之后也花了钱（`other_sessions` / `other_usd`）。
  有这笔才出现，因为**账本只记一个会话，所以看板上的钱也是下限**
- **对账状态**：上次对账时间 + 这 40 轮窗口里还有几轮没入账（`pending_in_window`）
- 本轮上下文占窗口的比例（过半变黄，八成变红）
- **按近 8 轮中位增速，还有几轮撞到 90% 窗口**
- 最近 16 轮的上下文柱状趋势（悬停显示每轮花费与命中率）
- 判断清单：这一轮该 handoff、该修前缀、还是该继续

「账本花费」是**上次 `sync` 那一刻**的快照，宿主累计（`ctx.cumulative`）一直在涨——两者差多少
≈ 上次对账之后又跑掉的钱。看板把「截至上次 sync」写在卡片上，不假装自己实时。

它是一个静态页 + 一个 JSON 接口，没有构建步骤，没有前端依赖。

要写脚本读 `/api/state`，用 `http.client` 直连。用 `urllib` 时如果本机设了 `HTTP_PROXY`，
请求会被代理吞掉（返回 502 而不是看板的 200）——这不是服务的问题，域名白名单加上 `127.0.0.1` 就行。

## 实测样本

在真实长会话上跑出来的样子（128k 窗口、中转 `deepseek-v4.1-flash`）：

```
某一轮上下文 74.7k tok（窗口 128k 的 58%）
构成 input 227 + cache_read 74.5k，本轮命中率 99.7%
近 8 轮中位增速 +711 tok/轮 → 距窗口 90% 还有 56 轮
这一轮 $0.000316（¥0.0021）（消息自带 cost）
```

含义很直接：**还没到要换手的时候，但按当前增速五十几轮后会到。** 这种"提前几十轮就知道"的信息，是压缩提示词给不了的。

`tg sync` 在同一个宿主的另一个长会话上跑出的对账（714 轮，真实 `session_message` 逐轮数据）：

```
本次同步 714 轮
新输入 2384.8k + 输出 360.5k（其中推理 215k）= 2960.3k tok
缓存读 45495.4k / 写 0 —— 不计入预算
钱：$0.276054（¥1.8466） · 宿主记录
```

两件事值得注意：**缓存读是新输入的 19 倍**——这个会话的账几乎全落在"重读已有上下文"上，
所以省钱的着力点不是少写两行新输入，而是**让每轮要重读的前缀变短**（压缩），或者干脆
**换个短前缀**（handoff）；**推理 token 占输出的 60%**——记账时漏掉它，钱就对不上。

完整输出见 `examples/example-sync.txt`。

## 局限（诚实清单）

1. 只认 OpenCode 的 sqlite 布局；其它宿主需用 `TOLLGATE_DB` 提供同构库。
2. 逐轮数据依赖宿主把 `tokens` 写进消息行；没有就退回采样差值，再没有就报"未知"——**不编数**。
3. 窗口大小取自配置的 `limit.context`，中转虚标就会算错占比。
4. `cost` 值是**上界**：中转的分组倍率通常还会打折。
5. 压缩比固定按 3:1 估，不实测（要用实测得先有压缩器，本项目不做压缩器）。
6. 增速用中位数，遇到"这轮突然读了个大文件"会滞后一轮才反映。
7. 不接管模型路由：`--tier` 只是标签，真路由靠会话内切模型。
8. 看板只读 + 采样，**不能从 UI 改计划**——写操作只走 CLI，才有 append-only 留痕。
9. `.plan/` 与 schema 2 与上游 `plan-ledger` 共享，改格式会同时影响两者。
10. `sync` 的归账边界是**步骤级**的：`tg start` 记下 `started_ms`，只算这之后的轮次。
    但边界只管时间：同一步里你先在 A 会话跑、又切到 B 会话跑，两边还得各 `sync` 一次
    （`sync --session <id>`）；边界也分不出「同一步里你顺手干了别的事」。
    （更早的版本连边界都没有，会把整段会话历史算给第 1 步——见反模式 #28。）
11. `sync` 读窗口是最新 2000 轮。更早的读不到，也就不计入；遇到超长会话时输出会明说，
    别把那次结果当成"会话总共花了多少"（那看 `tg ctx` 的会话累计）。
12. `sync` 只认带 `tokens` 的 assistant 消息。一轮里如果宿主没写 tokens，那轮就是漏记的，
    账本只保证"与宿主记到的一致"，不保证"与真金白银一致"。
13. `ctx` 只看最近 40 轮（`CTX_WINDOW`）。会话比这长时它**不说"第 N 轮"**——那个 N 只是
    窗口大小，不是轮次序号；谎报轮次比不报更坏。
14. `sync` 一次只认**一个**会话，所以账本里的钱是**下限**。同期在别处跑的花费（子 agent、
    另一个窗口、切回官方那个会话）不会自己进账本；`sync` 会点名报出它们合计多少，但要**你**
    决定要不要逐个 `tg sync --session <id>` 补账——它不替你判断哪个会话算这个任务的账。
15. 游标按会话分开存（`sync.json` v2），最多记 32 个会话、每个会话最近 2000 条 id。超了就按
    「最近同步」淘汰最久没动过的那个——被淘汰的会话下次再 `sync` 会整段重记。单个长会话的
    游标很大：1020 条 id ≈ 39 KB。
16. `plan.json` / `ledger.jsonl` 认 BOM（Windows 编辑器会加），但**只认 BOM**：手改 JSON 时
    结构写错、字段拼错，工具不会猜你的意思，该报错就报错。
17. `reconcile` 会把**所有**已完成步骤的门禁重跑一遍，所以计划里的慢断言会成倍放大时间
    （本仓 6 个步骤实测 352 秒，其中大半是两套全量测试）。它没有缓存、没有增量——「上次
    验过」不算数，这正是不骗人的代价。要给慢断言放宽时间用 `--timeout N`（`0` = 不限时）。
18. `tg start` 允许最多 2 步同时 `doing`（`--max-fanout N` 可调高），但**前提是每路
    一个独立会话**。两路塞进同一个会话里，轮次就混在一起了：`sync --step N` 点谁的名
    都是猜——账是真的、归属是假的。所以 `tg start` 放行时当场警告；有 2 步 `doing` 时
    `tg gate` / `tg sync` 不带编号会**直接拒绝**并把候选列出来，绝不「取第一个」。
    上限本身不是性能旋钮：15× token 换 +90% 质量、头号失败模式是 cost runaway，
    要更多路先回答「这几路各自产出的东西谁看、谁合、合不上怎么办」。
19. `orch rollup` 不加 `--gate` 时**不做**断言与语义的打架检测（因为 `status=done` 只说明
    「当时过了」，代码可能已经变了），并且明说「没查」。所以默认模式的 rollup **不能**
    当验收证据；要证据就加 `--gate`，慢但是真数据。
20. `--max-cost` 的刹车只连着**账本**，而账本是下限（见 #14）。所以它只会**提前**拦，
    绝不放行：已知花费到顶就拒绝 `tg start`。反过来说，如果你从不用 `tg sync`、只用手记
    `spend`，账本里就一项带真实 `cost` 的记录都没有——那时这个上限**拦不住任何东西**，
    `tg start` 会当场说出来，而不是让你以为有刹车。它也不管「没入账的花费」：
    同期别的会话多花了 $38，上限照样显示没到。
21. 语义层（reviewer）是**可选**的，而且它那层永远不能否决 `done`。接 `jev` 要一个云端 key，
    数据会离开本机；本区域直连还被 451 挡住，必须走代理——所以**代理一挂，这一层就整个不工作**
    （实测过：代理端口还在、CONNECT 也回 200，上游却是死的）。已验收程度与踩过的六个坑写在
    `docs/jev-onboarding.md`：合成 6/6、真步骤 3 次（`unsure 0.81` / `unsure 0.70` / `pass 0.99`）、
    机器抽查 13/13，**人工抽查 2/13 条 claim**（第 7 步第 4 条「多路 doing 时 `resume` 不替你挑」、
    第 8 步第 3 条「成环说清楚了」已由人确认；其余 11 条人还没看）——没看完之前它仍然只是「另一种看法」。
    另一个容易踩的：它给概率的敏感度很高，同一份代码换个证据就能从「不支持」变「verified」，
    所以 `reviewer` 不该被当成测量仪。想零外传就用 `reviewer=none`。

## 设计约束（四条，不破）

1. **零依赖** 只用标准库，Windows / macOS / Linux 同一份代码
2. **单一真相** `.plan/plan.json` 是唯一真源，`.plan/plan.md` 只是渲染视图
3. **追加写** `ledger.jsonl` / `ctx.jsonl` 只 append 永不改写，崩溃可恢复
4. **确定性门禁** 「完成」由断言 `exit code` 决定，不由模型自述决定
